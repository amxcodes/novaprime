# NOVA UI replan

**Status:** Current product and implementation plan · **Date:** 6 October 2026
**Design authority:** [`planbyaman.md`](planbyaman.md)
**Capability evidence:** [`ui-feature-capability-map.md`](ui-feature-capability-map.md), to be revalidated against the current migrations, API route dispatcher, command planners, and browser call sites before each feature is designed.

This document translates the design principles in `planbyaman.md` into decisions for NOVA. The design source remains authoritative for the visual language, adaptive workspace, design-system layers, customization principles, and future GenUI boundaries. This plan makes repo-specific decisions where the source leaves options open. NOVA's schema, current API behavior, access model, and user-approved white/green and black/green defaults constrain what can ship.

## Decisions to build from

| Area | Decision |
|---|---|
| Product visual language | Design a work-focused NOVA interface with authored domain visuals and strong information hierarchy. Use Apple-like restraint and precision as quality references, not as a copied visual skin. Do not default to generic card grids, blur, gradients, or decorative elevation. |
| Brand | White/green light mode and black/green dark mode are the defaults. Users can customize within accessible, validated choices. NOVA retains its name, words, icons, and interaction patterns. |
| Design authority | `planbyaman.md` owns design principles. This file owns the NOVA-specific rollout decisions. The older UI plan and execution blueprint are historical records until their claims are reconciled with the reset. |
| Frontend target | React + TypeScript, bundled with Vite, following the source plan's recommended component architecture. Migrate by route and vertical feature slice; do not replace the entire app in one cutover. |
| Styling | One global foundation for tokens, resets, typography, and accessibility preferences; CSS Modules beside feature and design-system owners. Components use semantic tokens, never hard-coded theme colors or one-off inline theme styles. Do not add Tailwind plus a second styling abstraction in the first pass. |
| Component behavior | Keep semantic native HTML where it gives a good accessible interaction. Use React Aria Components for the shared finite-choice `Select` popup because native popup rendering varies; retain a hidden native select for form submission and required-field semantics. `SearchableSelect` remains the separate control for searchable/large option sets. Validate both controls on desktop and real phone/tablet assistive technology before broadening use; keep replaceable implementation boundaries. |
| Backend boundary | The existing server, database, and API remain authoritative for identity, permission, scope, validation, and business rules. The client composes UI and calls typed API adapters; client-side feature visibility is discovery and presentation only. |
| Responsive model | One information model adapts through COMPACT, MEDIUM, and EXPANDED layouts based on available space. Initial viewport bands are hypotheses (`<640px`, `640–1023px`, `>=1024px`); validate them against actual content and container widths before treating them as fixed tokens. |
| Customization | Begin with persisted, bounded personal preferences and saved views already supported by the API. The current density contract intentionally exposes Comfortable and Compact; `planbyaman.md`'s third Default value needs a coordinated preference-contract revision before it is added. Structured workspace composition comes later. No executable configuration, arbitrary CSS, or permission changes through personalization. |
| Typography | Use Geist Variable as the working NOVA typeface, behind a semantic font token and system/Inter fallbacks. The normal WOFF2 subsets from Fontsource 5.3.0 are bundled under the design-system assets with their SIL OFL 1.1 license and imported through the foundation; Vite emits same-origin, content-hashed files. Fastly is a compatible delivery option if its service and origin are confirmed. Node, Vercel, and Netlify have immutable hashed-asset routing/configuration; Cloudflare delegates static delivery to Wrangler `ASSETS`. No exact Fastly service/origin configuration is present or verified. |
| GenUI | Future direction only. Any future generated composition must select from a trusted typed component registry and re-run normal authorization. No generated HTML/React, evaluation, or LLM-produced permission decisions. |

The React/Vite choice follows the source plan's framework recommendation and gives the feature-owned composition a typed module boundary. Vite's production build emits static assets suitable for static hosting, which fits NOVA's existing deployment model; all existing host adapters and API routing still need to be verified in the migration spike. [React's TypeScript guide](https://react.dev/learn/typescript) · [Vite production build](https://vite.dev/guide/build.html)

## Reset baseline (historical starting point)

At the user's direction, the previous visual layer was removed before this rebuild began. That snapshot is historical: the design foundation, route styles, feature modules, and preview tooling have since been restored incrementally.

- At reset, `web/index.html` loaded without a stylesheet and the former Settings presentation modules were absent. The current app has semantic tokens, an application shell, feature-owned CSS Modules, and locally bundled Geist font assets; a Fastly font origin is still unconfigured.
- API endpoints, command handlers, database access, authorization, and API-backed browser actions were retained through the reset. The server remains authoritative.
- The browser entry remains a large JavaScript route controller with extracted feature modules. It is migration debt, not the target architecture.
- Preference and saved-task-view API/data contracts were retained and their presentation has since been rebuilt against those contracts.
- `ui-design-plan.md` and `ui-revamp-execution-blueprint.md` include pre-reset status claims. Use them only where current source and this plan confirm their relevance.
- `ui-feature-capability-map.md` is useful inventory, not a substitute for checking current route/command code. Its client membership, client department, and WFH policy facts have been reconciled; verify other inventory claims before relying on them.

No endpoint or database behavior was part of the styling reset. Frontend migration must preserve every existing public/authenticated route, API call, permission boundary, deployment target, and recoverable form behavior.

## Product and permission model

### Visibility follows usable capabilities

Feature and action visibility must be driven by effective permission grants and supported scopes, never by role names such as “admin” or “manager.” Roles and their grants are configurable data. A page may be visible while some independent sections are not; a section may be readable while its actions are unavailable; every mutation remains target- and state-checked by the server. Server-reported Super Admin status is an explicit capability only where the corresponding endpoint uses it (for example, Owner Transfer); it does not grant unrelated Admin reads whose server handlers require ordinary permission grants.

**Capability architecture:** the current workspace destination registry owns route discovery/direct-route agreement; feature-owned planners own their read contracts; feature projections and server responses own action eligibility. A cross-layer regression test checks representative route/read-plan agreement. Do not introduce a second permission catalogue or a generic runtime evaluator unless a tested mismatch or repeated ownership-neutral rule demonstrates the need. Any future descriptor must consume—not reproduce—the server grant/scoping contract, and must not authorize an API call. If grant loading fails, protected UI fails closed; the server still rejects unauthorized reads and writes. Hiding a component must also mean its protected loader does not run.

Every surface distinguishes loading, empty, denied, partial, stale, and failed states. Independent panels load and fail independently. On identity change or access loss, protected records and drafts are cleared before the next identity's data renders. Unauthorized and out-of-scope record IDs must not be distinguished by the UI when the API intentionally gives them the same response.

## Target application architecture and ownership

Use the plan's layered architecture with NOVA-specific feature ownership. Page modules compose features; features own domain-specific UI, contracts, state, and styles; the design system owns reusable presentation mechanics; server modules retain policy and domain authority.

This tree describes responsibilities to grow toward, not directories to create for their own sake. Today, `web/app.js` and `web/app/` still own route dispatch, read planning, API transport, and host lifetimes; `web/src/app-shell/` owns shared navigation, grants, and frame behavior; `web/src/design-system/` currently contains foundations, primitives, and surfaces; and `web/src/features/` owns route and domain compositions, contracts, and CSS Modules. Personalization remains feature-owned under `web/src/features/personalization/`. `pages/admin/` now owns Admin route-level states, feature-slot lifecycle, and the tested grant-to-slot composition boundary. `WorkPage.tsx` and `MyDayPage.tsx` remain feature-local route compositions during the strangler migration; move them to `pages/` only when their route adapters are extracted, without duplicating API ownership. Extract host responsibilities by vertical route slice, and add controls, patterns, visual, `lib`, or page layers only when a stable shared responsibility justifies them. Do not scaffold empty layers to match this diagram.

```text
web/src/
  app/                  bootstrap, router, shell, identity lifecycle
  design-system/
    foundations/        tokens, reset, type, motion, icon contract
    primitives/         low-level layout and semantic building blocks
    controls/           button, field, select, menu, dialog, date controls
    surfaces/           popover, drawer, overlay, panel mechanics
    visual/             timeline, presence, progress, activity, relationship
    patterns/           filter bar, empty/error states, record list, form layout
    contracts/          component and visual contracts
  features/
    attendance/ work/ reviews/ people/ availability/ operations/
    work-context/ notifications/ settings/ admin/
  pages/                route-level composition only
  personalization/      appearance, navigation, saved views, workspace config
  lib/                  typed API client, auth context, permissions, dates
  test/                 fixtures, contract tests, visual/accessibility harness
```

Each feature follows one small, consistent shape where complexity warrants it: `api.ts` (feature endpoints/adapters), `contracts.ts` (DTOs and UI states), `capabilities.ts`, `components/`, `hooks/` or `state.ts` only for real shared state, feature-owned `*.module.css`, and focused tests. Do not create empty folders or split every 30-line component. Extract when a component has a stable responsibility, reuse, accessibility behavior, responsive contract, domain meaning, or meaningful isolated test.

Dependency direction:

```text
pages → features → design-system / lib
app → pages, identity and route composition
design-system ↛ features, pages, API policy, or personalization
browser UI → typed API client → existing server
```

The design system cannot know about “attendance” or permission keys. A feature may use shared primitives and semantic tokens, but feature layout/styles stay with that feature. Shared shell is limited to navigation, identity, page frame, and global interaction infrastructure; it does not become the dumping ground for every screen's CSS or data fetching.

### Migration strategy

Use a strangler migration with a single router/identity boundary. Keep the current renderer available until a route's complete capability, workflow, loading/error, browser, and deployment tests pass; then switch that route to the typed feature implementation. Do not mount the old and new renderers over the same URL at once. Extract API adapters and permission descriptors before or alongside each screen, so view migration cannot quietly change request shape or server authority. Avoid a permanent dual design system: the old renderer is a temporary route implementation with a removal criterion.

Start with one vertical slice, not a UI-kit rollout. The slice proves the app entry, typed API adapter, capability gate, shared shell, CSS Module/token pipeline, tests, history/direct-route behavior, and deployment asset graph. It should be possible to revert a route without reverting unrelated backend work.

## Design system and screen craft

### Foundations and visual rules

Use the source plan's primitive → semantic → component token hierarchy. Global tokens define brand/neutral ramps and spacing/type/radius/motion primitives; semantic tokens define canvas, surface, text, border, focus, action, success, warning, and danger; component tokens should exist only where a component contract needs a stable special value. Both themes derive from the same semantic vocabulary. Feature CSS consumes semantic tokens, never embeds palette hex values. A static test scans CSS declarations across React shell, design-system, and feature styles for hex values, common color functions, common named palette colors, and direct primitive-palette references; it permits `currentColor` and system colors only within forced-colors rules. A TypeScript-aware source check also rejects raw palette literals and direct primitive-palette references in statically declared JSX inline-style objects, while geometry styles and validated data-driven appearance previews remain allowed. Colors calculated inside arbitrary runtime helpers still require review by their feature owner.

The light theme uses a calm white/neutral canvas with deliberate green action and selected states. The dark theme uses deep black/charcoal surfaces and calibrated green accents with readable text hierarchy. Avoid pure black-on-pure-white at every layer, gratuitous shadows, gradients, glass, and tinting that changes meaning. Use solid surface hierarchy and separators first; reserve elevation for overlays. Status colors retain fixed semantic meaning even when users customize brand accent.

Geist Variable is the selected working face. Normal variable subsets from Fontsource 5.3.0 are retained under `web/src/design-system/assets/fonts/geist` with the SIL Open Font License 1.1; their `unicode-range` rules are imported through the design-system foundation so Vite emits same-origin hashed assets. The included subsets cover Latin, Latin Extended, Cyrillic, Cyrillic Extended, and Vietnamese; other scripts use system fallback. Keep `font-family` behind the `Geist Variable` semantic token, retain system/Inter fallbacks, and use `font-display: swap`. Do not preload every subset. Vite hashes imported assets; the Node static server explicitly serves hashed WOFF2 with the `font/woff2` MIME type and immutable one-year caching, and Vercel/Netlify have `/assets/*` immutable policies. Wrangler `ASSETS` is configured for Cloudflare, but deployed font response headers have not been inspected. No Fastly service/origin configuration is present in the repository, so do not describe Fastly delivery as configured. Never cache authenticated/API responses as shared static assets. [Fontsource package and license](https://fontsource.org/fonts/geist/about) · [Fontsource variable import and subset guidance](https://fontsource.org/docs/getting-started/variable) · [Fastly cache-control guidance](https://www.fastly.com/documentation/guides/full-site-delivery/caching/about-cache-control-headers/)

Build a component workbench before broad screen conversion. It contains default/hover/focus/pressed/disabled/pending/error states; both themes; supported density/type settings; long content; keyboard/touch operation; 200% zoom; reduced motion; and forced-colors review. Keep product visuals distinct from generic panels: attendance gets a workday timeline/pulse, reviews get a queue with explicit decision context, work gets a scannable list/board only where the query supports it, and people history gets a chronological/effective-date presentation. All data visualization uses a clear legend, accessible text alternative, and a non-color-only encoding.

### Responsive behavior

COMPACT, MEDIUM, and EXPANDED describe available content space, not device brand. Use viewport queries for the shell and container queries for feature layouts. Proposed first pass:

| Class | Starting width | Composition |
|---|---:|---|
| COMPACT | below 640px | One column; compact top bar and reachable navigation; bottom actions only for a small, stable primary set; detail and forms become single-pane; tables become labeled records or deliberately scroll within a named region. |
| MEDIUM | 640–1023px | Collapsible rail or drawer; two panes only when each retains usable width; toolbars wrap or overflow through an explicit menu; avoid desktop sidebars consuming most of a tablet portrait viewport. |
| EXPANDED | 1024px and up | Persistent navigation rail/sidebar where it earns its width; multi-column compositions only when content can support them; tables and secondary panes are available with clear hierarchy. |

These are starting bands, not immutable truth: test feature container widths and let evidence move the cutoffs. Support 320px minimum, 360/390px phones, 600px compact landscape, 768px tablet portrait, 1024px tablet landscape, 1280px and 1440px desktop, split-view/narrow windows, and 200% zoom. Preserve the same data and actions across sizes; change arrangement and affordance. Use at least 44px touch targets on coarse-pointer controls, visible focus, no clipped menus, and no horizontal page overflow. Dense data may scroll inside a clearly named collection, but the page itself must not become a sideways desktop canvas.

Responsive acceptance belongs to each feature owner. Test representative real rows, long names, translated/long labels, zero/maximum states, and permission-filtered content, not only empty screenshots.

### Interaction contracts

Every interactive control has consistent layout dimensions, spacing, keyboard/focus behavior, pending/disabled semantics, accessible name, error association, and touch behavior. Use one menu/dialog/drawer contract rather than route-specific popovers. A styled trigger with an uncontrolled native popup is insufficient when it causes a browser-default-looking product interaction; finite-choice `Select` now uses a React Aria popup while retaining native form serialization, and `SearchableSelect` owns searchable/large option sets. Preserve native controls only where their interaction and visual behavior meet the same bar.

The bounded primitive spike is complete. Native `<select>` with tokenized `appearance: base-select` preserves native control semantics, but popup styling is available in [Chrome 135+](https://developer.chrome.com/blog/a-customizable-select) and [Safari 27](https://webkit.org/blog/18325/webkit-features-for-safari-27-0/); [Firefox 149](https://developer.mozilla.org/en-US/docs/Mozilla/Firefox/Experimental_features) still lacks full picker styling by default. `base-select` replaces the built-in mobile OS picker with an in-page popup, so it does not meet NOVA's cross-browser consistency requirement by itself and needs device validation.

React Aria Components is now the implementation for the shared finite-choice `Select` popup; its hidden native `<select>` preserves named form submission and required-field semantics. `SearchableSelect` remains a separate design-system control for Work/Admin searchable and permission-scoped choices. Both controls remain subject to the browser and assistive-technology release gate above; do not broaden use until desktop and real phone/tablet checks pass. Public/auth legacy styles stay route-scoped during migration.

Forms keep values after recoverable errors, clearly identify field and form failures, prevent duplicate submissions, and clear protected data on authentication/access loss. Confirmations are reserved for material or hard-to-reverse actions. Motion explains state changes and respects reduced-motion preferences. Empty states explain why there are no records and only offer actions supported by current grants.

## Personalization and workspace scope

Personalization changes presentation, never capability. Resolve visual settings in this order: system defaults → organization defaults when an authorized contract exists → role defaults only when explicitly persisted and authorized → personal settings → current view context. Missing or invalid configuration falls back to a safe default without removing a working workflow.

### Initial UI rebuild

Reintroduce only preference controls that have a current persistence contract and are validated by the API:

- theme mode and curated/custom accessible accent;
- density, text scale, contrast, motion, surface, and content width where the preference schema supports them;
- typeface selection limited to approved faces, including NOVA Geist and device/system fallback;
- permitted navigation ordering/pinning and home selection;
- allowed My Day module ordering/visibility;
- owner-scoped saved Work filters/views.

Preferences do not grant access: hidden or pinned navigation destinations are intersected with current grants each time. A previously saved route that loses access disappears from navigation and its direct route is denied. Keep notification preferences in their own contract; do not store credentials, business records, permission grants, or shared defaults in a personal appearance object. Cross-device revision conflicts offer an explicit reload/overwrite choice and reset only the requested scope.

### Later structured workspace

First deliver a strong default, then a separate Normal/Customize mode. The first workspace editor is a constrained responsive grid/ordered module list: move/reorder, pin, show/hide eligible modules, choose home, preview, save, and reset. Modules come from a typed trusted registry with stable ID, feature owner, required capabilities, data contract, responsive modes, size constraints, and user configuration schema. Store validated configuration only; unknown/removed module IDs are discarded safely. Critical policy/security notices, required workflow steps, and authorization messages cannot be hidden or moved in ways that change their meaning.

Do not build freeform drag/resize, three per-device layouts, organization/role defaults, shared-view publishing, undo/redo, or AI workspace generation in the first release. Add those only when user evidence and versioned API/schema contracts justify the persistence and migration cost. The default responsive layout adapts automatically; users should not have to curate a phone, tablet, and desktop copy.

## Quality and release checks

- **Authorization:** role names never substitute for effective permission keys/scopes; hidden features issue no request; deep links and every action are server-checked; no protected data survives actor/access changes.
- **Composed feature access:** each feature owns its grant plan and declares the exact read grants, action grants, scope intersection, and optional child capabilities it needs. Treat authorization, operational eligibility, and data readiness as separate inputs: a role policy flag does not authorize data; source facts do not grant access; and one feature grant never silently grants another. `attendance.check_in`/`attendance.check_out` authorize self-service commands, not payroll or attendance visibility. Payroll remains a future capability: a payroll screen requires its own effective payroll read/action grants, and any attendance detail surfaced inside it needs an explicit scoped permission. Payroll calculation may consume approved attendance source facts through a server-owned contract without exposing the attendance feed to payroll users. Missing check-in/out grants hide those actions but do not by themselves make a person payroll-ineligible; no payroll grants means no payroll route, dashboard module, fetch, or detail. New permission keys require a catalogue entry, server-enforced command/read contract, feature-owned capability mapping, navigation/dashboard mapping, and tests proving hidden features do not fetch.
- **Role dashboard composition:** custom roles do not receive role-name templates. The shared shell and dashboard are composed from the person's current effective grants and scopes, then the user's saved layout can order or hide only those authorized modules. When grants change, refresh the capability projection before protected content is reused; server denials remain authoritative and clear stale protected data.
- **Operational policy dependencies:** dependent switches must be explicit and fail closed in both UI and database. Payroll attendance contribution and overtime eligibility require payroll eligibility; disabling the parent clears its dependent values. The role editor enforces this relationship before submit, while database constraints remain the final check.
- **Responsive:** test compact/medium/expanded widths above, small tablet in portrait/landscape, split view, zoom, touch and pointer, long content, real populated records, and overlay clipping.
- **Accessibility:** keyboard-only operation, screen-reader names/relationships/announcements, visible focus, contrast, 200% zoom, forced colors, reduced motion, semantic tables/forms, minimum touch size. Target WCAG 2.2 AA.
- **State coverage:** loading, empty, denied, partial, stale, error, pending, success, validation, conflict, offline/network failure where supported, and expired authentication.
- **Visual system:** both default themes and supported preferences; token-only theme colors; no native-browser styling leaks on NOVA product dropdowns; component spacing and control alignment reviewed at actual sizes.
- **Maintainability:** feature-owned composition/styles/contracts; no page-specific rules in global shell; no circular design-system imports; typed API boundary; named removal point for each legacy route.
- **Deployment:** build and smoke-test static assets, SPA/direct routes, API forwarding, font resolution, cache headers, and rollback on every supported target. Vite hashes imported assets; deployment adapters must publish the generated graph rather than hand-maintaining source asset rewrites. [Vite asset handling](https://vite.dev/guide/assets)

## Explicit non-goals

This plan does not redesign API behavior or database policy as part of styling, fabricate functionality because a visual example looks useful, replace the backend with client rules, turn every feature into a card, introduce a huge component kit, provide arbitrary user CSS, build separate desktop/tablet/mobile products, expose unscoped organization data, or start GenUI. Backend additions may be proposed when the capability inventory identifies a necessary gap, but they require their own data, permission, migration, and operational contracts.
