# NOVA UI feature and capability map

> **Audit snapshot (7 October 2026):** This map is an evolving inventory, not the final permission oracle. Some UI/style observations predate the visual reset; the Work, People, reviewer-management, and Availability cursor notes below have been reconciled with the current working tree. Validate route and permission claims against source before implementation.

This is a focused, historical capability inventory paired with the [current NOVA UI replan](nova-ui-replan.md). The replan owns product information architecture, visual rules, responsive behavior, architecture, and rollout phases. This document records which user-facing components were found in the schema/API comparison, what was missing, and where data contracts limit UI claims; validate each item against current route and command source before implementation.

## Evidence and interpretation

The database inventory follows the repository's ordered migration source through the latest migration, **0079**. Personal appearance/workspace preferences first appear in **0075**; **0076** adds operator updater checksum metadata; **0077** moves bounded personal task views into their owner-scoped table and removes the legacy field from generic preferences; **0078** adds an organization-scoped access revision used to invalidate stale Availability agenda cursors after grant, role assignment, role archival, or office/department assignment changes; **0079** adds a permission-catalogue flag that keeps new permissions unavailable to customer-created roles until a shipped feature is deliberately enabled. Existing grants are retained, and payroll catalogue entries remain reserved. Migrations are the schema source of truth for this audit. Their presence does not prove that a customer's hosted database has applied them. The audit does not infer product capability from an isolated historical QA snapshot or from rows in a customer database.

“Observed” below describes current browser, API, and migration source. “Missing” describes absent or incomplete source paths identified in that comparison. “Recommendation” is a proposed UI/API increment, not a claim that it exists. Read/write permission checks still belong to the authenticated API; browser predicates only control discovery and presentation.

## Cross-feature access contract

NOVA already has a configurable role and permission system with independently scoped grants. Scope can include organization, own record, office, organization department, client, client workstream, group, or assigned work. Role grants are effective-dated and combined for the current actor. Operational eligibility, target state, and business rules remain additional gates. Migration [0079](../database/migrations/0079_permission_customer_role_assignability.sql) controls which catalogue entries customers may add to custom roles; it is separate from runtime authorization. The API still checks effective grants on every protected read and command, and the client derives feature visibility from those grants. When a catalogue entry is unavailable for customer roles, the editor retains any legacy grant unchanged while preventing new assignment or edits to that grant. The domain model and initial scope catalog are in [migration 0001](../database/migrations/0001_people_identity.sql), with scope validation and later scope additions in [0024](../database/migrations/0024_permission_scope_catalogue.sql), [0031](../database/migrations/0031_client_access_permission_scopes.sql), [0044](../database/migrations/0044_collaboration_scope_catalogue.sql), and [0045](../database/migrations/0045_tasks_create_client_scope.sql).

Observed client navigation now uses [workspace destination descriptors](../web/workspace-destinations.js) for current signed-in destinations. The same predicate controls menu visibility and direct route entry; the home fallback order also comes from those descriptors. [Admin feature descriptors](../web/admin-read-state.js) add permission-key and supported-scope discovery for the current sections. Invite-only access surfaces Invite without surfacing the broad Admin destination. Protected commands remain independently authorized in server modules.

The current client has a destination registry, Admin section descriptors, and target-scoped action hints, but not a complete record/action capability catalogue. Admin, Work, and Operations now plan independent reads from the actor's effective permission scopes; hidden features issue no fetch, and allowed reads show independent error states. Work assignment and request rows carry server-derived action capabilities so narrow roles see only the actions they can currently attempt. `GET /api/reviews/pending` is actor-owned, filtered by the current `tasks.review` target grant before its 100-row limit, and read-only; reviewer-unavailability repair remains in the maintenance path. `GET /api/tasks/:taskId` now provides an uncapped, exact-record `tasks.view` projection with no-store headers; task-scoped assigned-work viewers receive only their own assignment summary, and the DTO omits email addresses. Review access remains separate. Office creation explicitly requires both organization settings and geofence management. A purpose-limited office selector supports geofence managers, and self-review scopes are excluded from actionable review sections. Some other APIs may still return empty arrays when a grant is absent, and the full record/action capability catalogue remains incomplete.

Recommendations:

- Extend feature descriptors through records and actions, then reuse them for navigation, route entry, section discovery, loaders, and action visibility.
- Extend feature descriptors through remaining record/action surfaces and legacy read paths; keep each component hidden without its required permission or purpose-limited capability, and keep one panel's failure from erasing other authorized panels.
- Re-check permission and target state on every command. If a read or write returns 403 after access changes, clear the affected protected records, selections, and drafts.
- Availability continuation cursors now include an opaque access revision derived from the organization revision and the actor's currently effective agenda grants (including scope targets and assignment dates). Migration [0078](../database/migrations/0078_organisation_access_revisions.sql) advances the revision on role/grant, effective assignment, and person/office/department organization-move changes. Its `SECURITY DEFINER` revision helpers are private trigger plumbing with public execution revoked. A stale or pre-0078 cursor receives a restart-required 409; the feature clears retained events before requesting page one again, and a fresh 403 moves to the denied state. Focused server/client contract tests cover cursor validation, revision mismatch, row clearing, and restart. The rolled-back database fixture [0078](../database/tests/0078_organisation_access_revisions.sql) covers backfill, trigger changes, and request-organization RLS, but PostgreSQL execution is still pending in CI because local Docker/WSL/PostgreSQL is unavailable.
- Test grants and scopes as independent dimensions. Role names are customer-defined data and are not authorization rules.

## Domain feature map

### 1. Account, organization, roles, and people lifecycle

**Database and API capability.** Migrations [0001–0007](../database/migrations/) establish organizations, offices, departments, people and identity links, person status periods, employment terms, roles, operational policies, permission definitions and scoped grants, invitations, audit events, authentication, setup, and onboarding. Later migrations add auth handoffs ([0052](../database/migrations/0052_auth_system_handoffs.sql)), public-origin settings ([0056](../database/migrations/0056_public_origin_settings.sql)), and role revision concurrency ([0065](../database/migrations/0065_role_revision_concurrency.sql)). API reads include organization, offices, departments, permissions, roles, people, and audit events; commands cover setup, invitation, onboarding completion, role changes, freeze/offboard, and owner transfer. Route dispatch is in [server/src/app.ts](../server/src/app.ts); command implementations are under [server/src/commands](../server/src/commands/).

**Observed UI.** The browser has sign-in, reset/accept-invitation, and first-run setup pages. Admin remains one route, while Roles, Availability configuration, People/onboarding/lifecycle, Organization Structure, Attendance Policy, and recent Audit Events are separate React feature surfaces with feature-owned contracts and CSS Modules. Admin's page section map filters those features by effective grants; Attendance Policy is passed as a typed child with a minimal policy projection, while the host retains the endpoint and protected command. Availability configuration is now a typed lazy child in that same composition: the feature projector allowlists and validates shift, calendar, holiday, office-choice, and shift-selector data, while separate view/manage grants control each resource and its actions. Calendar managers retain the independently authorized shift choices; office targets remain unavailable without `organisation.settings.manage`. Loading and chunk/render errors are contained within the section. The host preserves the existing three POST endpoints and payloads, command lifetime and current-grant checks, and server authorization. Geofence is also a typed lazy child under organization-scoped `availability.office_geofence.manage`; it receives only the purpose-limited office ID, name, coordinates, and radius projection. Roles and Permissions now enters the same grant-filtered composition as a typed lazy child with a feature-owned safe projection; organization-scoped `roles.view` controls its reads and section, while `roles.create` and `roles.edit` independently control their actions. `roles.assign` does not expose the role editor. Office, department, and work-context selector reads remain independent; unavailable targets are distinct from errors and empty authorized lists. A wrapper-chunk failure is contained to the Roles section, preserving other authorized Admin features. The host retains the existing role endpoints, revision payload, live grant checks, and server authorization. The Admin host projects only the server-authorized People rows, rechecks effective grants before commands, and retains ownership transfer as a separate Super Admin-only flow. Invite is also a separate legacy route. Freeze actions follow the permission catalogue's organisation, office, or department scope against each target person; the authoritative command checks the target's current effective office/department, and matching scoped freeze administrators receive the event. Main implementations are [web/app.js](../web/app.js), [PeopleAdministration.tsx](../web/src/features/admin/PeopleAdministration.tsx), [OrganizationStructure.tsx](../web/src/features/admin/organization/OrganizationStructure.tsx), [AttendancePolicySettings.tsx](../web/src/features/admin/attendance-policy/AttendancePolicySettings.tsx), [AuditEvents.tsx](../web/src/features/admin/audit/AuditEvents.tsx), [RolePermissionsSection.tsx](../web/src/features/admin/roles/RolePermissionsSection.tsx), [RolePermissionsEditor.tsx](../web/src/features/admin/roles/RolePermissionsEditor.tsx), [AvailabilityConfigurationSection.tsx](../web/src/features/availability/AvailabilityConfigurationSection.tsx), [admin-configuration-projection.ts](../web/src/features/availability/admin-configuration-projection.ts), [AdminAvailabilityConfiguration.tsx](../web/src/features/availability/AdminAvailabilityConfiguration.tsx), [admin-read-state.js](../web/admin-read-state.js), [freeze-person.ts](../server/src/commands/freeze-person.ts), and [offboard-person.ts](../server/src/commands/offboard-person.ts).

**Current Admin read limits.** Office and department lists require organization-scoped `organisation.settings.manage`; the office endpoint can include archived rows but does not return an archive marker, so the UI must not label every row active. Attendance policy read and write also require organization-scoped settings management; the read selects against database `current_date`, while a policy change is validated against the actor's business date. The audit endpoint requires organization-scoped `people.view`, returns no cursor or total, and the current screen requests the newest 50 events. The host strips target identifiers and raw `details` before rendering. These are existing API semantics; changing them requires a separate backend contract decision.

Organization Structure now enters the grant-filtered Admin composition as a typed lazy child. Its feature-owned projection forwards only office ID/name/location/timezone/coordinates/geofence radius and department ID/name, while office and department read states fail independently. The section requires organization-scoped `organisation.settings.manage`; department creation uses that same grant, while office creation remains gated by both organization settings and `availability.office_geofence.manage`. Loading, module failure, and render failure retain a single feature heading. Existing endpoints and server authorization are unchanged; the UI does not label offices as active because the read response has no archive marker.

**Admin composition boundary (4 October 2026).** WFH Overrides, Leave Review, WFH Review, People/onboarding, Owner Transfer, and Admin Work now enter the same grant-filtered `AdminPage` as typed children with feature-owned projections/fallbacks and route adapters. WFH list and create stay separately gated. People retains the organization-only legacy roster read, separate invite grant, target-scoped lifecycle checks, and separately authorized onboarding selectors; invite-only and scoped directory viewers do not trigger the full roster. Owner Transfer requires a healthy server-reported Super Admin read and an independently authorized organization-scoped `people.view` target list. Admin Work is split into context creation, task composition, task operations, and client memberships; each child loads only behind its existing grant/read condition and has a local failure state. `web/app.js` remains the permission/read/API and page-lifetime orchestration host; isolated adapters bind feature props and existing commands, and the server continues to authorize each read/write. Membership targets are projected from the authorized host result, loaded on expansion, and kept mounted while collapsed to preserve state. The expanded-target callback only cancels stale UI work after collapse and does not grant access. Focused Admin Work components pass 9/9 tests; its four route-adapter suites and three composition tests pass 23/23, and Admin section, capability, loader, projection, and grant suites pass 45/45. The Vite build transforms 1,677 modules; its main entry is 477.48 kB (142.66 kB gzip), with Admin Work composition and membership-target UI in separate lazy chunks. No authenticated populated-role, device/screen-reader, or PostgreSQL-backed end-to-end QA was done for this slice. See the [current replan](nova-ui-replan.md) for full verification and chunk metrics; no endpoint or database contract changed in this UI slice.

**Current UI and remaining work.** The People destination now has a responsive directory/history workspace: expanded widths show the selected record beside the directory; medium and compact widths show detail with a keyboard-safe return to the selected row. Selection remains URL-backed and directory state stays mounted during in-place transitions. Direct/deep-linked person history does not trigger a directory read. Remaining work is independently gated profile sections and a fuller person-record experience only if product scope requires more than bounded effective-dated history of office, department, role, employment terms, and status periods. History is not a complete personnel dossier, and Admin invitation/onboarding/lifecycle remains a separate workflow. Split organization structure, access/roles, and operator settings into focused destinations without changing their existing API ownership.

**Effective checks.** Use `people.view`, `people.create`, `people.edit`, `people.invite`, `people.activate`, `people.freeze`, `people.offboard`, and `roles.assign` independently. The bounded People directory supports organisation, office, or department `people.view`; the Admin full roster uses the legacy `GET /api/people` endpoint and requires organization-scoped `people.view`. Invitation is organization-scoped; freeze/offboard affordances are checked against each target's current office/department. Onboarding completion currently requires all three organization-scoped grants `people.edit`, `people.activate`, and `roles.assign`. `roles.view/create/edit/assign` and `organisation.settings.manage` control their own subsections. Preserve the protected Super Admin rules and separate a permission grant from role operational eligibility. Manual auth handoff and public-origin access have distinct gates (`auth.manual_recovery`, `organisation.public_origin.manage`); email-provider administration is Super Admin restricted.

**API/data limits before UI promises.** The dedicated `GET /api/people/directory` uses server-side literal search and bounded keyset pages (25 by default, 50 maximum); its cursor is bound to the normalized query and it returns no total. Both directory pages and the exact-target `GET /api/people/:id` summary recheck `people.view` at organisation, office, or organisation-department scope, with target filtering before paging. Direct/deep-linked selection loads only the exact-target summary and separate bounded history read; selection within an already-authorized directory reuses its identity-matching summary and loads exact-target history. The legacy `GET /api/people` is an unpaginated, organization-grant-only roster used by Admin selectors and other legacy callers; Operations now uses the bounded directory endpoint. Do not change the legacy envelope without migrating those callers. History covers the five categories above and is not a complete personnel dossier. Do not imply that a directory row is a full personnel file or render identity subject/token data. Onboarding's mutation permissions do not grant its selector reads: offices/departments currently require `organisation.settings.manage`, roles require `roles.view`, and managers come from the authorized People projection. The UI reports these prerequisites rather than treating missing options as empty. A purpose-limited selector read would require a separate API/permission design. Invitation endpoints may return HTTP 202 with a staged manual handoff or a delivery error; distinguish these from successful email delivery. The `people.freeze` server check now matches current target office/department membership, aligning it with migration 0024 and role-grant validation; contract tests assert the target and effective-date predicates, but no PostgreSQL transaction fixture runs that command. Admin, Work, Work Setup, Operations, My Day, Availability, and People use permission and purpose-limited capability checks to gate route access and feature reads; Settings gates operator sections independently, while Notifications uses actor-owned self-service reads. A reusable record/action capability catalogue remains incomplete, and some APIs still return empty collections when grants are absent.

**Role target directory limitation.** The role editor's scoped-grant choices are assembled from separately authorized office, department, and work-context reads. A role manager without those domain reads can still see the role editor but cannot select every valid scope target. The current UI disables only scopes whose target list is unavailable, explains the required read grant, preserves an existing saved target for deliberate replacement, and distinguishes unavailable lists from authorized empty lists. This is a documented backend/API limitation rather than unfinished UI behavior. Consider a minimal target-directory read gated by `roles.view` only as a separate API/security design; do not reuse or broaden the existing domain reads implicitly.

### 2. Clients, workstreams, groups, departments, and membership

**Database and API capability.** [Migration 0016](../database/migrations/0016_work_context_collaboration.sql) adds clients, client and organization workstreams, work groups, tasks, and assignments. [Migrations 0030–0033](../database/migrations/) add client departments and effective-dated client memberships, scope checks, overlap prevention, and integrity rules. `GET /api/work-context` returns authorized context and creation targets. The current client-access routes are `POST /api/clients/:clientId/departments` (create only, no department-list route) and `GET`/`POST /api/clients/:clientId/members` plus `PATCH /api/clients/:clientId/members/:membershipId/end`, implemented in [server/src/commands/client-access.ts](../server/src/commands/client-access.ts) and dispatched in [server/src/app.ts:331–343](../server/src/app.ts).

**Observed UI.** Admin Work now enters the grant-filtered page as a typed `AdminWorkSection` with independently lazy-loaded context creation, task composer, operations, and client-membership children. The host maps only authorized projections into each slot: current context/create scopes drive context creation; `tasks.create` independently gates task composition; the existing task read plan drives operations; and `clients.members.manage` plus server-filtered target data drives membership. `web/app.js` retains API transport, read/grant planning, identity/page/snapshot guards, and route orchestration; isolated adapters bind each feature's current props and existing commands. Client target membership reads start only on first expansion; the mounted editor remains hidden on collapse to preserve its state, and the live target-current callback invalidates adapter work after collapse. That callback is a UI lifecycle guard, not an authorization check. A separate lazy Work Context feature renders authorized clients, workstreams, and groups as a hierarchy; create-only groups appear as eligible task targets without revealing their surrounding hierarchy. The route host also projects server-returned `taskCreationTargets` that are omitted from the browsable hierarchy into a minimal, separate list of non-navigable task-target labels; it deduplicates these against visible workstreams and strips billing/group metadata. Search remains local to the authorized response, retains visible parent context for browse matches, and includes the separate create-only target labels without making them browseable. A client department form appears only under an explicitly returned client with organization-scoped or exact-client `clients.departments.manage`; workstream-only inferred client context does not qualify. The explorer exposes no membership or general edit actions. See [AdminWorkSection.tsx](../web/src/features/admin/work/AdminWorkSection.tsx), [AdminClientMembershipTargets.tsx](../web/src/features/work-context/AdminClientMembershipTargets.tsx), [admin-work-context-creation-route.js](../web/app/admin-work-context-creation-route.js), [admin-task-composer-route.js](../web/app/admin-task-composer-route.js), [admin-work-operations-route.js](../web/app/admin-work-operations-route.js), [admin-client-memberships-route.js](../web/app/admin-client-memberships-route.js), [WorkContextExplorer.tsx](../web/src/features/work-context/WorkContextExplorer.tsx), [WorkContextCreation.tsx](../web/src/features/work-context/WorkContextCreation.tsx), and [work-context.ts](../server/src/commands/work-context.ts). No authenticated populated-role/device/screen-reader or PostgreSQL-backed end-to-end QA was run for this slice; component, route-adapter, typecheck, and production build results are in the [current replan](nova-ui-replan.md).

Admin Work discovery is now limited to current workflows with usable target reads: client-scoped workstream creation needs visible client context; group creation needs its parent workstream visible; broad task editing needs matching `tasks.view`, and assignment/reassignment also needs a usable `people.view` selector. Assigned-work editing stays in Work/Mine. Client/workstream/group edit grants do not expose this Admin section because matching edit workflows are absent. `tasks.reviewer_manage` independently exposes the reviewer-management feature in Work; it does not expose Admin Work or assignment-management controls.

**Missing UI.** Admin already has a capability-gated client-membership panel that can read pages, add memberships, and end open memberships. Work Context is still not a server-searchable/pageable directory or navigable client/workstream detail experience; its search cannot discover rows absent from the current response. Department creation is create-only; department listing, selection data, and full management remain unavailable because the API has no department-list/read route. A role with only `clients.departments.manage` also has no client-name discovery path: `GET /api/work-context` and the membership read do not return targets for that grant. This is an API-blocked capability, not permission to display guessed targets or broaden the explorer. Add any future target search/paging as a separate minimal read that returns only active client IDs/names authorized by the effective department-management grant; keep the existing department POST as the final authorization check. Add navigable record detail, breadcrumbs, and department management only as supporting target-scoped contracts allow. Scope each row and selector to authorized targets.

The Work Context create-only form calls the existing `POST /api/clients/:clientId/departments` route after checking the current exact-target grant and visible-client allowlist. No client-department list or manager UI exists. Do not describe `clients.departments.manage` as an implemented department-management screen.

**Effective checks.** Use `clients.view/create/edit`, `clients.departments.manage`, `clients.members.manage`, `workstreams.view/create/edit`, and `groups.view/create/edit` at their client/workstream/group targets. Verified client membership GET, POST, and PATCH-end commands require `clients.members.manage` at organization scope or for the exact client; the end command binds both `clientId` and `membershipId`. Client department creation requires `clients.departments.manage` at organization scope or for the exact client. `GET /api/work-context` also includes a client target for organization- or client-scoped `clients.members.manage`; this is only the server-filtered context projection, not independent permission to browse that client's hierarchy. A `tasks.create` grant does not by itself authorize every context read or membership change.

**API/data limits before UI promises.** Client departments have a create route but no list/read, update, or archive route. Client memberships have a bounded, cursor-paged GET (default 50, maximum 100), a POST add route, and a PATCH end route at `/clients/:clientId/members/:membershipId/end`; there is no general membership update route. The end command accepts `effectiveUntil`, binds the membership to the given client, rejects already-ended rows, and validates the end date against both the start date and the person's current business date. These routes require `clients.members.manage` or `clients.departments.manage` at organization scope or for the matching client, respectively. Permission keys such as `clients.edit`, `workstreams.edit`, and `groups.edit` are not evidence of implemented rename/archive routes. `GET /work-context` filters archived entities out for new-work context; archive/rename mutation semantics remain undefined, so do not add archive/delete controls. The work-context result is not a complete browse/search API for all client records and has no browse pagination.

**Missing UI and persistence.** Shared organization defaults, group visibility, My Day module sizes, collection columns/layout/board choices, record peek/full-page preference, and shared-view publishing/overrides remain unimplemented. Verify Geist requests and cache headers on the selected deployed host/CDN; no Fastly origin is configured or confirmed, and do not expose a free-form font URL. Organization defaults and shared views need separate authorization, revision, and audit behavior; personal appearance must not mutate them. Saved view query data must use its dedicated owner-scoped contract rather than generic appearance JSON.

**Effective checks and limits.** Appearance and task views are personal and owner-bound; no new UI-preferences role permission exists. Organization defaults and shared views need explicit capabilities and server APIs before controls appear. Appearance/workspace and task-view schemas are independently versioned at v1. Do not put permission choices, domain statuses, arbitrary CSS, credentials, or generic workflow definitions into user appearance JSON. Migration 0076 concerns updater checksum metadata, not a customer UI capability.

### 9. Payroll and billing boundary

**Observed database/API state.** The role policy has payroll applicability flags, and the permission catalogue includes future payroll view/manage/lock keys. The task billing model records NOVA's automatic billable/non-billable classification and immutable source on task/session records. The migration chain through 0077 contains no payrun/calculation model or payroll execution API.

**UI boundary.** Keep payroll execution, payruns, payslips, calculations, invoices, rates, and payment actions out of this UI backlog. Existing policy flags and permission metadata describe future eligibility; they are not payroll records or an executable payroll feature. Expose billing classification only where it helps explain the workstream rule and immutable task provenance. See [NOVA PRD payroll boundary](../NOVA%20PRD.md) and the explicit scope statement in [the UI plan](ui-design-plan.md#decisions-and-scope).
