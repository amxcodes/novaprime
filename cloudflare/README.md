# NOVA on Cloudflare + Supabase Cloud

This is the hosted adapter for the same NOVA API and PostgreSQL schema. It
does not add a second domain implementation: Cloudflare supplies the request
runtime, Hyperdrive supplies the PostgreSQL connection, and the selected
background scheduler calls `/api/internal/background/tick` every five minutes.

1. For Supabase Cloud, open the project's **Connect → Direct connection**
   settings and use that database endpoint with the restricted `nova_app`
   credentials generated by `bun run setup:supabase`. Do not use the Supabase transaction-
   pooler URL written to `DATABASE_URL`; Hyperdrive connects to the database
   directly and provides its own connection pooling. Keep the `nova_app`
   password in Hyperdrive, then copy only the configuration ID into the
   selected Wrangler file (`cloudflare/wrangler.toml` or
   `cloudflare/wrangler.supabase-cron.toml`). The ID is a binding reference,
   not a password. Netlify/Vercel Node runtimes use the generated transaction-
   pooler `DATABASE_URL` instead. Each Worker request creates short-lived
   `pg` clients for NOVA and Better Auth; Hyperdrive owns connection reuse
   across requests. Do not retain a process-global `pg.Pool` in the Worker.
2. In Cloudflare → Worker → Settings → Variables & Secrets, set
   `BETTER_AUTH_URL` to the public HTTPS origin and add optional
   `NOVA_ALLOWED_ORIGINS` / `NOVA_PUBLIC_ORIGIN` as plain runtime variables.
   Add these four as Worker secrets; never commit them:

   ```text
   BETTER_AUTH_SECRET
   NOVA_BACKGROUND_JOB_SECRET
   NOVA_BOOTSTRAP_TOKEN
   NOVA_SECRETS_ENCRYPTION_KEY
   ```

   All Wrangler configs set `keep_vars = true` so these dashboard-managed
   origin variables survive later GitHub deployments. The scheduler selector
   remains defined by the chosen Wrangler config. The Worker trusts
   Cloudflare's edge client-IP header for auth throttling;
   do not reuse `NOVA_TRUST_PROXY_HEADERS=true` on a direct VPS unless its
   reverse proxy strips and rewrites forwarded headers.
3. Apply the canonical `database/migrations` to the chosen PostgreSQL
   project, then deploy from Workers Builds with
   `npx wrangler@4.141.0 deploy --config cloudflare/wrangler.toml`.

Both configs declare Cloudflare's Version Metadata binding. NOVA reports the
immutable Worker version ID through its protected deployment-identity
endpoint. For a release upload, tag the version with the exact full Git commit
SHA (`wrangler versions upload --tag <commit-sha>`); only a valid Git SHA is
reported as the release. This makes identity checks detect an unexpected
version and connect a tested candidate to its source commit. Version URLs use
the uploaded version's existing bindings, including production Hyperdrive and
secrets. Cloudflare preview/version URLs are public by default when enabled.
Zero Trust Access is optional for NOVA's public runtime and is not needed for a
candidate test. Use `wrangler.runtime-candidate.toml` for that test: it deploys
a separate `nova-runtime-candidate` Worker on the account's public
`workers.dev` hostname, disables version preview URLs, and declares no Cron.
Do not use `wrangler.supabase-cron.toml` for a candidate; it has the production
Worker name `nova` and changes that Worker's deployment.

Because the candidate hostname is public, give it a disposable Supabase/Postgres
target through a separate Hyperdrive configuration, use the restricted
`nova_app` role, and configure the candidate's own `BETTER_AUTH_URL`,
`NOVA_ALLOWED_ORIGINS`, and `NOVA_PUBLIC_ORIGIN` to that exact hostname. Use
NOVA's normal sign-in and feature permissions for authenticated read-only page
checks. Do not use a customer database or migration-owner credentials for this
public candidate. Keep `NOVA_BACKGROUND_SCHEDULER` set to the scheduler that
actually owns the disposable database; the candidate itself has no Cron and
must not receive the Supabase Cron callback. Its `workers.dev` URL is public,
not a secret or an access-control mechanism; see Cloudflare's
[workers.dev](https://developers.cloudflare.com/workers/configuration/routing/workers-dev/)
and [Preview URL](https://developers.cloudflare.com/workers/versions-and-deployments/preview-urls/)
documentation.

Deploy and verify it with:

```text
npx wrangler@4.141.0 deploy --config cloudflare/wrangler.runtime-candidate.toml
```

This verifies the remote Worker/Hyperdrive path, static assets, candidate
authentication origin, and bounded read-only endpoints. It does not promote
the customer hostname or prove traffic cutover, rollback, or a same-database
runtime move. Those remain separate gates. The deployment manager continues to
require its verified Access boundary before it accepts a public version URL as
a production move candidate. See
[Version Metadata](https://developers.cloudflare.com/workers/runtime-apis/bindings/version-metadata/),
[Version URLs](https://developers.cloudflare.com/workers/versions-and-deployments/version-urls/),
[Hyperdrive local development](https://developers.cloudflare.com/hyperdrive/configuration/local-development/),
and [Access application destinations](https://developers.cloudflare.com/api/resources/zero_trust/subresources/access/subresources/applications/methods/list/).

Cloudflare Workers use outbound HTTPS email adapters: Gmail API OAuth2 or
Resend. Gmail API OAuth2 uses Google's HTTPS token and send APIs; it does not
use SMTP or Gmail-account passwords. SMTP/Nodemailer is unavailable in the
Worker runtime and NOVA rejects it there before saving or activating it.
Node/Netlify/Vercel/VPS runtimes can use SMTP/Nodemailer as well. If email is
not configured or its provider is unavailable, NOVA uses the same secure
system-handoff path across deployment types.

## Select the background scheduler

The default `wrangler.toml` selects Cloudflare Cron and sets
`NOVA_BACKGROUND_SCHEDULER=cloudflare`. When Supabase Cron/pg_net is selected
instead, deploy the same Worker with the explicit no-Cron configuration:

```text
npx wrangler@4.141.0 deploy --config cloudflare/wrangler.supabase-cron.toml
```

That config sets `crons = []` so a prior Cloudflare trigger is removed, and
sets `NOVA_BACKGROUND_SCHEDULER=supabase`. For a new scheduler setup, run
`bun run supabase:scheduler` from a trusted operator machine after the API is
ready. During a runtime move with an already active Supabase job, leave that
job and its Vault values unchanged; do not rerun the scheduler setup command.
If later
switching back to Cloudflare Cron, deploy with `cloudflare/wrangler.toml` and
first run `bun run supabase:scheduler:disable` so only one trigger remains.

For a Netlify → Cloudflare runtime move where Supabase Cron is already active,
use this no-Cron config and keep the existing Supabase job and Vault callback
unchanged while testing the Access-protected Worker version URL and promoting
the same public hostname. Do not point the production job at the candidate
version URL or create another schedule. Verify the existing job's recent
`pg_net` response before promotion and again after the hostname reaches
Cloudflare. If Netlify Cron still owns scheduling, complete and verify the
Netlify-to-Supabase scheduler handover separately before starting the runtime
move. Changing the Supabase callback origin is a post-promotion operation and
requires verifying the next `pg_net` response.
